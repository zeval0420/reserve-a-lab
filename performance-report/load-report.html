Main findings

  • Time behaviour is good up to 100 concurrent users. At the expected peak of 50 users the median response was 25 ms and the p95 187 ms, with no errors in 17,182 requests. Up to 100 users the p95 stayed below 200 ms.
  • Capacity is at least 200 users (p95 ≤ 10 s and errors ≤ 5%). At 200 users the median stayed at 24 ms but the p95 rose to 4.14 s: about one request in ten waited 2–6 s. The 300-user step was stopped by the host for low memory before it finished, so the upper limit was not measured.
  • The 200-user slowdown is most likely Apache's thread limit, not CPU. Apache on Windows serves each connection with one of 150 threads and keeps idle connections open for 5 s. With more users than threads, a request on a new connection waits for a thread; the delay sits in time-to-first-byte, is bounded by the 5 s keep-alive timeout, and appears only above 150 users, while CPU averaged 34% of the machine.
  • Response time climbs as data accumulates. In the 30-minute soak, the admin approvals page went from a median of 166 ms in the first 5 minutes to 4.9 s by minute 25, because it renders every pending request on one page (about 4,000 by the end). Apache and MariaDB CPU rose with it at constant load. Memory showed no growth in the first 15 minutes, before other programmes on the laptop began to interfere.
  • Double booking: FAIL before the fixes (PASS after them: 1 approved of 20 in every repetition). When 20 approvals of the same lab, date and time were sent at once, 20, 20, 19, 18, 17 of 20 were approved in the five repetitions (the correct number is 1). It also happens without any concurrency: approved 3 seconds apart through the real page, all 3 of 3 were approved.
  • Inventory over-allocation: FAIL before the fixes (PASS after them: 2 approved, stock never below zero). 20 requests for 2 of the last 5 units were all approved in every repetition (40 units allocated against 5 in stock), and the stock went below zero (−1) in 2 of 5 repetitions. The inventory page's manual deduction, which locks the row, passed the same test 5 of 5 times.
  • The Lighthouse improvements are statistically significant for performance score (+25.1 points, paired t-test p < .001), FCP (−2.22 s, t-test p < .001), LCP (−5.00 s, Wilcoxon p .0078) and page weight (−1,246 KB, Wilcoxon p .0078), n = 8 pages.

Safety and test data

  • Only localhost was tested. The database dbadmin was backed up with mysqldump before testing and restored afterwards; all 47 tables matched their pre-test checksums after the restore.
  • Every test started from the same baseline (original data plus synthetic accounts and test items), restored before each run, so later tests are not affected by rows created by earlier ones.
  • Submissions and approvals send notification e-mails through Gmail SMTP inside the request. Outbound SMTP from Apache was blocked with a Windows Firewall rule for the duration (connections fail in under 40 ms), and every address in the database was replaced with an @example.invalid address. No e-mail left the machine.
  • Load-journey materials used 10 synthetic consumables with 1,000,000 units each, so real stock was never drawn down.
  • No application code was changed. The inventory deduction log table, which the inventory page needs but which was not present locally (its migration was removed in commit 8f9d971), was created from that migration for the control test and removed by the restore.

Definitions

Response time = k6 http_req_duration (request sent to last byte received). Percentiles use linear interpolation. Error rate = requests with an HTTP error, timeout, connection error or functional failure (for example a lost session or a refused submission) divided by all requests. CPU is shown as a percentage of the whole machine (16 logical processors), so 6.25% equals one fully busy core. Memory is the private working set.

The slow requests were spread evenly over the 3-minute hold (about 85 per 10 seconds) and concentrated in four endpoints: the conflict check, the request form, admin approvals and approve request. These are the requests that follow a 3–10 s think time. The delay was in time-to-first-byte (p95 4.0 s), while the TCP connection was accepted within 13 ms, and the slow responses clustered between 3 and 5 s. Machine CPU averaged 34% and at least 4 GB of memory stayed free. This matches Apache's Windows thread model: 150 worker threads, each held by an idle keep-alive connection for up to 5 s. With 200 users, a request that arrives on a new connection after a pause longer than the keep-alive timeout waits until another connection times out. At 100 users (fewer connections than threads) there is no such tail. This explanation fits all observations but was not confirmed by changing the Apache configuration, which was outside the scope of this test.

Test 5. Concurrency and double booking

Each repetition starts from the restored baseline. All virtual users log in and load their pages first, then wait for the same wall-clock instant (a barrier set in k6 setup()) before sending the critical request. The largest gap between the first and last request at a barrier was 4 ms. After each run the database was queried directly; the query output is reproduced below as evidence. These are the results before the fixes; the re-runs after them are in After fixes.

Why. The approve action (ajax/ajax_admin_action.php, force_approve, line 117; the same applies to the multi-stage path in ajax_supervisor_action.php) updates the request to Approved without checking the slot on the server, without a transaction or row lock, and without a unique constraint in the database. The only check is a separate check_conflict call that the browser makes before showing the approve dialog. The race runs gave every admin the most favourable client: each ran that check correctly and skipped the approval if it reported an approved conflict. Even so, 17–20 approvals went through, because all checks ran before any approval was written (a check-then-act race). Only the few admins whose check arrived after another approval had been written were stopped (0, 0, 1, 2 and 3 per repetition).

It also fails without concurrency. The approvals page sends check_conflict without the csrf_token field the endpoint requires (admin_approve.php line 1604 against ajax_forms.php line 446), so the browser receives HTTP 403 and never shows the "Severe Conflict" warning. In the control run, three admins approved three requests for the same slot 3 seconds apart through that real page path; the page's check returned 403 each time, a correctly sent check would have reported "approved" for the second and third, and the server approved all three. The live warning on the request form (forms.php line 1327) has the same missing field. The submission endpoint actually used by the form (ajax_supervisor_action.php) has no slot check either.

After fixes

The three concurrency failures above were fixed on the server side (branch fix/concurrency) and tests 5a, 5b and 5c were re-run with the same scripts, the same 20 simultaneous teachers and admins, the same baseline restored before every repetition and the same database queries. The Before columns below are the original runs, unchanged and still shown in full above; the After columns are the re-runs. The database was backed up before the re-runs and restored afterwards; outbound SMTP was blocked again for the duration.

What changed
  • Approval is one transaction (scilab_approve_request() in helperFiles/variableDeclarations.php), used by force_approve and approve in ajax/ajax_admin_action.php and by the final stage of the multi-stage path in ajax/ajax_supervisor_action.php. It locks the lab's scilab_availability row (SELECT … FOR UPDATE), refuses if an approved request for the same lab and date overlaps, then updates the status and deducts stock. A refusal rolls everything back.
  • Stock: scilab_deduct_inventory() locks the item rows (SELECT … FOR UPDATE, in id order), refuses the approval with a message if any item has too little stock, and deducts with WHERE quantity >= ?, the same pattern as the inventory page's manual deduction. No schema change.
  • Submission (request_submission) refuses a slot that an approved request already holds.
  • Conflict warning: admin_approve.php and forms.php now send the csrf_token field with check_conflict, so the "Severe Conflict" warning can show again.

  • Behaviour change: approval is now refused when stock is short, where it used to approve and deduct what was left. For reagents, submission checks the total across rows but the deduction takes from one row, so a request spread across rows can pass submission and be refused at approval.
  • The SMTP block was in place, so notification e-mail time is not included, as in the original runs.

Interpretation

Nielsen's response-time limits

Nielsen (1993) gives three limits: 0.1 s feels instantaneous, 1 s keeps the user's flow of thought, and 10 s is the limit for keeping attention on the task. The table counts endpoints by the band their p95 falls in.

At the expected peak of 50 users, 17 of 20 endpoints answer within 0.1 s at the 95th percentile and the rest within 1 s. The three that exceed 0.1 s are the actions that write and send e-mail (submit request, approve request) and the admin approvals page, which grows with the number of pending requests. No endpoint reaches the 10 s limit at any load up to 200 users; at 200 users four endpoints move into the 1–10 s band at the 95th percentile, where users notice the delay but stay on task. In the soak test only the admin approvals page left the 1 s band, because of data growth.

Resource utilizationSatisfactoryApache used 2.3% of the machine's CPU at 50 users and 10.8% at 200; MariaDB below 3% up to 200 users. No memory growth in the undisturbed first 15 minutes of the soak (no sign of a leak). CPU per request rises as the request table grows.

Functional correctness is a separate ISO/IEC 25010 characteristic (functional suitability), but the concurrency results belong in the same discussion: the system stays fast under concurrent use but does not keep its booking and stock rules under concurrent use, or in the slot case even under sequential use through the real page.

Limitations

  • Local laptop, not the campus server. Server, database and load generator shared one laptop, which also ran other programmes. k6 used up to 14% of the machine's CPU at 200 users and competed with Apache. Memory pressure from other programmes stopped the 300-user step and disturbed the last half of the soak test. Absolute numbers on the campus server (different CPU, memory, operating system, possibly Linux with a different Apache MPM) will differ.
  • No network. Requests never left the machine, so there was no network latency or bandwidth limit. Real users on the campus network or mobile data will see longer times; the Lighthouse report covers the front end on a throttled connection.
  • E-mail excluded from the timings. With SMTP blocked, each notification attempt failed in milliseconds. In production every submission and approval sends its e-mails through Gmail inside the request (in the test database an approval attempted 36–56 notification e-mails and a submission 1–2), so real submit and approve times will be longer, possibly by seconds.
  • Simulated users. Virtual users follow two scripted journeys with random think times; real users browse less regularly, use other pages and do not all submit a request every session. The 80/20 split and the think times are assumptions. Every session logged in afresh. Browser caching and static files were not part of the load.
  • Synthetic data. 505 synthetic accounts were added (they lengthen the teacher list in the request form). Requests accumulated faster than in real use (one per requester session), which makes the data-growth effect on the admin approvals page appear within minutes; in real use it would build up over weeks if pending requests are not cleared.
  • Capacity is a lower bound. The 300-user step did not finish, so capacity is reported as at least 200 concurrent users.
  • Lighthouse statistics. n = 8 pages is small; the pages are not a random sample, and each value is a median of 3 runs. The About-page LCP value is the published median (17.7 s) because its saved report is a different run (14.6 s).
  • MariaDB counters. FLUSH STATUS did not reset the server's status counters in this setup, so per-run MariaDB counters are not reported.
